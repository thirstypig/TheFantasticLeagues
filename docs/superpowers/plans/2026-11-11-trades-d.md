# Trades (step D) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Style Bible screens 16–18:
- 16 New trade (owner): pick a team, tick what you give and get, add auction dollars, roster check for both sides, send (or keep it until trades open)
- 17 Trades (owner): offers to you with Accept / Reject on the card, your offers with Cancel, done this season
- 18 Trades (commissioner): accepted trades with Veto / Process, unanswered offers, processed trades with Reverse

**Architecture:**
- Reuses the existing trade engine (`server/src/features/trades/routes.ts`): propose, accept, reject, cancel, veto, process, reverse. **No schema change, no migration.**
- Small server changes only: one pure roster-count helper shared by propose / accept / process, a fix to the process check, propose-time validation, and `GET /api/trades/window`.
- Owner pages live in `client/src/features/trades/pages/`; the commissioner page in `client/src/features/commissioner/pages/` with its own wrappers in `commissioner/api.ts` (ADR-015: no cross-feature imports).

**Tech Stack:** Express + Prisma + Zod, React 18, React Router 6, Vitest + Testing Library + supertest.

**Spec:** Style Bible screens 16–18 (https://claude.ai/artifact/UDWjhsrCsDKxovbSjkyPXc#screens; repo copy `client/public/style-bible/index.html`), roadmap step D card (https://claude.ai/artifact/2ZwcUjSmsWTMZ34GjCU5vS#d), the trade flow in the Style Bible ("Owner A proposes → Owner B accepts or rejects (A can cancel before then) → Commissioner processes or vetoes; rosters change only here → can be reversed later"), and James's direction: no needless scrolling, phone and desktop versions of every screen, no modals except irreversible confirms.

## Decisions taken at planning time (rulings)

1. **Process-time roster check is wrong today; fix it.** `POST /:id/process` counts every unreleased row (IL included) against a hardcoded 23. A team with one IL player has 24 rows, so even a 1-for-1 trade fails. New rule, used at propose, accept and process: count active rows only (`assignedPosition !== "IL"`), compare to the league cap (`loadLeagueRosterCap`), and fail only a team whose count goes **up** and ends **over** the cap. A team already over cap can still make an even or shrinking trade. Cost if wrong: a trade that should be blocked goes through; the commissioner still has to Process it.
2. **Assets offered in the new screens: players and auction dollars only** (`PLAYER`, `BUDGET`). No picks, future dollars or waiver priority (OGBA trades dollars, not picks). Dollars can go either way, capped at the sending team's `budget`. Trades that already hold other asset types still display by label.
3. **IL players can't be picked** in the new trade screen (shown with "On IL", not tickable), and propose rejects them on the server. Trading an IL player carries an IL slot to a team that may have none free. Cost if wrong: an owner must activate first.
4. **Outside the trade window, the trade is kept in the browser** (`localStorage`, key `fbst.tradeDraft.v1.<leagueId>`). The button reads "Trades open at the next meeting" and is disabled; nothing is scheduled on the server. Cost if wrong: switching devices loses the draft.
5. **No "Note to <team>" field.** `Trade` has no note column, and this step adds no migration. Deferred.
6. **No stats on player rows yet** (".271, 22 HR" in the mockup). Rows show position · MLB team. Stats come with step E's player data.
7. **No "You approve every trade" switch.** Process is always required today; the commissioner page states the rule instead of offering a switch that does nothing.
8. **Meeting-day processing is dated like meeting moves.** On screen 18, if no period is active and a pending period exists, Process sends `effectiveDate = <pending period startDate, YYYY-MM-DD>`; otherwise it sends none (server uses tomorrow). Reverse sends none.
9. **Legacy pieces:** the legacy "Record Retroactive Trade" tool (`CommissionerTradeTool`) moves to `/commissioner/:id/trade-record` (via `CommissionerSectionPage`, like "Backdated fixes" in step C) and is linked from screen 18 as "Record a past trade ›". Activity's Trades tab is left as it is in this step.
10. **Owners reach trades from the League tab**: a "Trades" link right after "Activity" in `navModel.ts`. `/trades` stops redirecting to `/activity`.

## Review Focus

1. **A roster changed after the offer was sent** (player dropped or traded elsewhere). Accept and Process must fail with a clear message; Process must not silently skip a missing player. → Task 1 test `process rejects a trade whose player left the sender`.
2. **Team with IL players makes a 1-for-1 trade.** Must succeed at propose, accept and process. → Task 1 test `IL rows do not count toward the cap`.
3. **Uneven trade (2-for-1).** The receiving team over cap is blocked before sending; the team going under is told it fills the spot at the meeting. → Task 2 `tradeCheck` tests.
4. **Window closes between build and send / between offer and accept.** Server already 409s; the screen shows the message and keeps the draft. → Task 3 test `keeps the draft when send returns 409`.
5. **Double tap / stale list.** Two quick taps on Accept, or acting on a trade someone else already answered: the second call's 400 shows on the card and the list reloads. → Task 4 and Task 5 tests `reloads after a 400`.
